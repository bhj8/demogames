# 转向长帧修复 · 2026-09-22

上一轮在新图集第一次进入视野时调用 `renderer.compile`，为检查一个合批材质反复遍历整场景。这会阻塞浏览器主线程并等待 GPU，鼠标事件无法及时处理。现有输入本身没有新增插值或延时队列。

修复将 18 个图集批次、着色器链接检查、纹理上传和首次微型绘制移到菜单阶段；只对怪物及所需光照编译一次。开始按钮准备期间显示“正在准备画面…”，完成后恢复。网络请求等待有 12 秒上限，超时仍可使用可见回退模型。战斗绘制不再创建批次、遍历全场景编译或查询 GPU 链接状态。

保留缺图重试、模型回退及合批失败时的逐只绘制；移除过度保守的 varying 数量预判，以实际程序链接结果判断兼容性。另防止重复点击开始按钮启动多条主循环。鼠标灵敏度、镜头朝向与武器摆动参数未改。

## 同机对照

Chrome / Windows / RTX 2070 SUPER，1920×1080，每档 180 个真实动画帧，持续转向。`before.json` 为修改前，`after.json` 为修改后。怪物包含 15 类；修复后等待菜单准备完成再测进入游戏后的帧。

| 怪物数 | 最差帧间隔：修改前 → 后 | 最差渲染 CPU 耗时：修改前 → 后 |
|---|---|---|
| 5 | 287.7 → 18.7 ms | 290.0 → 2.3 ms |
| 150 | 467.6 → 36.0 ms | 452.6 → 5.6 ms |
| 900 | 666.0 → 54.0 ms | 650.5 → 14.3 ms |

战斗期间的材质编译次数均降为 0。900 怪的平均帧间隔由 21.8ms 到 18.2ms，95 分位仍约 18.1ms，收益主要是去除首次出现时的长帧。数字是该测试环境的帧耗时，不是物理鼠标到显示器的端到端延迟，也不保证所有设备相同。

## 回归

- 18 个批次都在开始前完成准备，正常环境没有失败程序。
- 鼠标事件即时更新 yaw/pitch；下一游戏帧镜头方向与输入计算值一致，含反向和零位移检查。
- 重复触发开始只建立一条主循环。
- 15 类怪物与额外三档破甲的缺图、慢加载、自动重试、低顶点属性、着色器失败回归通过，900 个实例仍是 59 次绘制。
